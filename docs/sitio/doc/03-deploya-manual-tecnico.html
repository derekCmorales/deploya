Introducción

Este manual explica cómo se instala, se configura, se despliega y se opera Deploya. Está escrito para tres lectores:

  • Quien evalúa o prueba el proyecto y quiere levantarlo en su computadora con un comando (capítulo 3).
  • Quien opera el servidor de la nube de Deploya: publicar una versión, respaldar, vigilar (capítulos 5 y 7).
  • Quien instala Deploya en su propio servidor con el modo autoalojado (capítulo 6).

Nota

Todos los comandos se corren desde la raíz del repositorio (github.com/derekCmorales/deploya) salvo que se diga otra cosa. Los nombres de archivos y variables son los reales del repositorio.

Instalación local

Requisitos

ParaNecesitas
Levantar todo con Docker (recomendado)Docker con Compose v2 y 4 GB de RAM libres

Levantar la plataforma con un comando

git clone https://github.com/derekCmorales/deploya.git
cd deploya
cp .env.example .env
# Edita .env y define ADMIN_CLAVE (obligatoria)
docker compose up --build

Compose arranca en orden: postgres y redis (con healthcheck), luego migracion (aplica las migraciones y el seed, y termina), luego api, worker, traefik, mailpit y web.

Desarrollo fuera de Docker

pnpm install
docker compose up postgres redis mailpit     # solo la base, la cola y el correo
set -a; . ./.env; set +a
pnpm --filter @deploya/api exec prisma migrate deploy
pnpm --filter @deploya/api prisma:seed
pnpm dev:api                                 # http://localhost:3001 con recarga
pnpm dev:web                                 # http://localhost:3000 con recarga

Con MOTOR_ADAPTADORES=stub (valor de .env.example) el motor corre en memoria: los despliegues avanzan por sus etapas sin Docker, útil para trabajar en la interfaz. Con MOTOR_ADAPTADORES=docker se usan BullMQ, git, Docker y Traefik reales, y hace falta el worker.

Cuidado

Si se pierde CLAVE_CIFRADO_VARIABLES, las variables de entorno guardadas de todos los proyectos quedan ilegibles y sus despliegues fallan. En el servidor solo vive en .env.vps (permisos 600), nunca en el repositorio ni en Terraform, y se guarda aparte de los respaldos. También cifra las contraseñas de los recursos de datos.

Despliegue en AWS

El piloto corre en una EC2 creada con Terraform (ADR 0009): la misma plataforma de docker compose que en local, más HTTPS y el certificado comodín. La landing vive fuera del servidor, en S3 y CloudFront, para que siga arriba aunque la EC2 se reinicie (ADR 0011). Ningún secreto pasa por Terraform.

Primera puesta en marcha

Requisitos: Terraform 1.9 o más, AWS CLI v2 con el plugin de Session Manager y credenciales de la cuenta.

cd infra/terraform
cp terraform.tfvars.example terraform.tfvars   # dominio y correos del presupuesto
terraform init
terraform plan -out=piloto.tfplan
terraform apply piloto.tfplan
terraform output siguientes_pasos             # imprime los pasos con la IP y el ID reales
  1. DNS en Cloudflare, en «Solo DNS»: lo que imprime terraform output registros_dns.
  2. Esperar a cloud-init (5 a 10 min): aws ssm start-session --target <id> y cloud-init status --wait. Deja Docker, el usuario deploya y el repositorio en /srv/deploya.
  3. Copiar .env.vps dentro de la sesión de SSM, sin que pase por Terraform ni por un chat: sudo -iu deploya, cd /srv/deploya && umask 077 && cat > .env.vps y chmod 600 .env.vps.
  4. Publicar: RAMA=main scripts/desplegar-vps.sh.
  5. Guardar CLAVE_CIFRADO_VARIABLES fuera del servidor.

desplegar-vps.sh es idempotente: hace git pull --ff-only de la rama, genera la ruta de la plataforma para Traefik, corre docker compose --env-file .env.vps -f docker-compose.yml -f docker-compose.vps.yml up -d --build, repite migraciones y seed y espera a que la API responda. Cada publicación posterior es solo ese comando.

Con HOST_WEB=app.<dominio> la web queda en app.<dominio>, la API en api.<dominio>, cada proyecto en <proyecto>.<dominio> y el S3 de un proyecto en <proyecto>-s3.<dominio>. La raíz es la landing.

Landing en S3 y CloudFront

La landing es un sitio estático de Astro en el repositorio deploya_landing. Se publica con AWS CLI desde ese repositorio:

LANDING_BUCKET=$(terraform -chdir=infra/terraform output -raw landing_bucket) \
LANDING_DISTRIBUCION=$(terraform -chdir=infra/terraform output -raw landing_distribucion) \
pnpm deploy:aws     # aws s3 sync + invalidación de CloudFront

La primera vez, ACM necesita ver los CNAME de validación en Cloudflare antes de emitir el certificado: terraform apply -target=aws_acm_certificate.landing, crear los registros de registros_dns_validacion_landing y repetir el apply.

Modo autoalojado

Deploya es de código abierto (AGPL-3.0) y se instala en un servidor propio. En autoalojado no hay cobro: un único plan «Autoalojado» sin vencimiento, límites por proyecto que fija el administrador y registro abierto, con invitación o cerrado (ADR 0008).

./scripts/instalar.sh                  # instala por etapas
./scripts/instalar.sh --continuar      # retoma después de corregir lo que falló
./scripts/instalar.sh --sin-comodin    # certificado por HTTP-01 si no hay token DNS
./scripts/instalar.sh --codigo-nuevo   # genera otro código de configuración
EtapaCompruebaAplica
1 · RequisitosDocker 24+, Compose v2, curl, dig, openssl—
2 · DominioQue la raíz y un nombre del comodín resuelvan (registro A, no CNAME) a esta máquina—
3 · CertificadoToken del proveedor DNS o, con --sin-comodin, el puerto 80Estrategia DNS-01 o HTTP-01
4 · Servicios—.env con permisos 600 y secretos generados (32 bytes), compose up, migraciones
5 · Administrador—Imprime una sola vez el código de configuración (vence en 30 min); solo su hash sha256 va al .env

Con el código, se abre https://<dominio>/configurar: el asistente pide el código, crea la cuenta de administrador, prueba el SMTP (o sigue sin correo) y elige la política de registro. Lo guardado vive en la tabla ConfiguracionInstalacion, no en archivos, y se cambia después en Admin · Instalación.

Operación

Actualizar y respaldar

./scripts/respaldar.sh                         # base + configuración, sin la clave de cifrado
./scripts/respaldar.sh --restaurar AAAA-MM-DD  # vuelve a un respaldo
./scripts/actualizar.sh                        # respalda, migra y reinicia api, web y worker
./scripts/actualizar.sh --volver               # restaura el respaldo previo a la actualización
  • respaldar.sh guarda la base y la configuración, conserva los 7 más recientes y no pisa dos respaldos del mismo día. La clave de cifrado no entra al respaldo: se guarda aparte.
  • actualizar.sh no detiene los contenedores de las apps de los clientes: solo reinicia la plataforma.
  • Además, Data Lifecycle Manager toma un snapshot diario del disco completo y guarda 7: es la copia fuera del servidor.

Recursos de datos: respaldo y restauración

Cada PostgreSQL, Redis o S3 que crea un cliente es un contenedor deploya-datos-<subdominio>-<tipo> con un volumen del mismo nombre (ADR 0012). El volumen sobrevive a despliegues, reversiones y reinicios; solo se borra al eliminar el recurso o el proyecto dueño.

docker system df -v | grep deploya-datos-               # uso de disco por volumen
C=deploya-datos-nimbo-api-postgres
docker exec $C pg_dump -U deploya -Fc app > app.dump    # respaldo lógico sin detenerlo
docker exec -i $C pg_restore -U deploya -d app --clean < app.dump

Importante

El disco se mide y se avisa (usoDiscoMb frente a discoDatosMb del plan), no se corta. Restaurar un volumen completo desde un snapshot de DLM está paso a paso en docs/infra-vps.md §5.

Generar esta documentación

Los cuatro documentos viven como HTML en docs/sitio/doc/, con el design system v4.1 en modo claro, y se publican tal cual en Cloudflare Pages junto con sus PDF. Los diagramas salen de los .mmd de docs/diagramas/.

pnpm diagramas:sync                    # los .md y .mmd al día
node scripts/docs-sitio/construir.mjs  # diagramas, índice con páginas y los cuatro PDF

El script redibuja los diagramas marcados, genera cada PDF con Chromium, numera el índice con las páginas reales (con pdftotext) y vuelve a generar el PDF. El sitio queda en docs/sitio/: Cloudflare Pages lo sirve sin paso de construcción.
